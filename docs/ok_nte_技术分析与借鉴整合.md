# ok-nte 技术分析与借鉴整合

> 分析日期：2026-08-08
> 目标仓库：https://github.com/BnanZ0/ok-nte（《异环》后台自动化工具，Python 3.12 + PySide6，基于 ok-script 框架）
> 本文记录：技术方案分析、与本工程的对照、按优先级落地的借鉴点及实施状态。

## 一、ok-nte 技术方案全景

### 1.1 视觉层（三层递进）

| 层次 | 技术 | 用途 |
|------|------|------|
| 模板/特征匹配 | ok-script Feature 系统 + SIFT（Lowe ratio + RANSAC 单应性）+ 旋转模板缓存 | 定位固定 UI 元素，容忍缩放差异 |
| 目标检测 | YOLO26s（Ultralytics 训练，OpenVINO 编译，FP16，动态输入分辨率 1536x896，单类 target） | 战斗中角色/目标检测 |
| OCR | OnnxOCR | 文字兜底读取 |

关键预处理工具（集中在 `src/utils/image_utils.py` / `game_filters.py`）：
- `binarize_bgr_by_adaptive_center`：取 ROI 中心 50% 区域用 **Otsu 自动求阈值**，再全图二值化——不依赖固定亮度阈值。
- `binarize_bgr_by_adaptive_brightness`：平均亮度 + offset 得动态阈值，但要求高亮像素占比 ≥5%，否则判定"当前帧没有合格高亮内容"直接置黑——**过渡帧/异常帧检测做进了预处理**。
- `restore_world_brightness`：取灰度直方图前 1% 亮度百分位，将其拉伸到 255（仅当画面整体偏暗时），修复被游戏滤镜压低的场景亮度。
- `current_char_filter` / `current_char_detector`：用 **Lab 色空间 a/b 对手色通道**（chroma = √((a-128)²+(b-128)²)）而非亮度/HSV 提取彩色标记——"目标在光照下变苍白，但其颜色关系比任何亮背景更接近模板"，对亮度变化免疫。判定采用双阈值 + 第一名与第二名 margin + 0.8s 粘滞（低置信短暂保持上次值）。

### 1.2 声音层（WASAPI 进程环回，源自 ZZZSoundTrigger，GPL-3.0）

- 捕获：`ActivateAudioInterfaceAsync` + `AUDIOCLIENT_ACTIVATION_PARAMS` 进程环回（Win10 19041+），**只捕获目标进程树音频**，内存中 float32 分块，低延迟（5ms 缓冲），不写文件。
- 匹配：环形缓冲 0.2s 窗口、25ms 检测步进 → 4 阶 butter 高通滤波（1000Hz 截止）→ 波形归一化（除以 std）→ FFT 互相关（scipy `correlate` mode="same"）→ 最大相关系数作为匹配分数。
- 触发：双阈值（闪避 0.13 / 反击 0.12）、0.5s 防连发、监听循环崩溃 1s 自动重启。
- 样本：wav 预处理结果缓存为 `.npy`（缓存键 = 采样率/滤波参数，mtime 校验）。

### 1.3 工程层

- **资源约束**：OpenVINO 推理显式 `INFERENCE_NUM_THREADS=2` 限制线程（"降低 CPU 峰值负载"）；AVX2 能力检测降级。
- **异步推理**：infer request 轮换 + force 抢占 + **request 延迟销毁（retired 保留 3s）**——防止 C++ 回调线程未退出时 Python GC 触发 GIL 死锁。
- **VisualTemplateCache**：进程级并发安全缓存（get_or_build 单构建者 + 异步预热 + 代际失效）。
- **LogGate**：日志门控——按 key 间隔节流 + `changed=True` 时**消息内容变化才记录** + callsite 自动 key。
- 架构：AGENTS.md 约束架构边界、tests/ 纯逻辑单测优先、i18n（gettext）、CI 自动构建签名发布、uv 锁文件。

## 二、与本工程对照：可借鉴点与优先级

### 优先级 1：自适应二值化替代固定白色掩码 ★★★

**背景**：本工程用固定阈值白色掩码（r>190）提取行动值数字。2026-08-07 的 96→9 事件根因已证实：数字切换的过渡帧（淡入淡出）半透明，白色掩码仅捕获到 9 的高亮笔画，4 低于阈值丢失 → 误识别 9 → 骤降误拒绝。

**借鉴方案**（ok-nte 自适应二值化三件套）：
1. 正常路径仍用固定白色掩码（行为不变）；
2. 当主掩码像素数异常偏低（疑似过渡帧）时，回退到 **Otsu 自适应阈值**（在 ROI 灰度上自动求阈值）重新提取掩码；
3. 若 Otsu 结果仍低于最低像素数 → 判定低置信帧，走闸门拒绝而非硬识别。
另可选叠加 `restore_world_brightness`（直方图百分位拉伸）作为低亮度帧预处理。

### 优先级 2：日志 changed 模式（LogGate 精简版） ★★

**背景**：本工程已做"隐藏高频噪声"（窗口捕捉、未检测到进度条），但监控日志仍是每帧记录。

**借鉴方案**：实现精简 LogGate——按 key 节流（interval）+ 消息变化才记录（changed）。同回合行动值不变时不刷屏，变化瞬间完整记录。

### 优先级 3：识别结果缓存 ★★

**背景**：监控循环每帧对同一 ROI 做完整识别流程（掩码 + 分割 + 多模板匹配）。

**借鉴方案**：VisualTemplateCache 的单线程简化版——缓存最近一次 ROI 的内容指纹（下采样均值哈希），指纹未变则直接复用上次识别结果，跳过模板匹配。游戏画面静止（回合等待动画循环）时零成本。

### 优先级 4：声音通道（WASAPI 进程环回 + 音效模板匹配） ★★★（已确认游戏存在固定音效）

**背景**：画面识别在动画过渡帧上存在固有盲区；音频维度不受画面渲染影响。

**借鉴方案**：
1. **样本采集工具**：录制一段含目标音效的游戏音频（wav），工具自动按能量突变切分事件片段，供用户确认后保存为模板；
2. **监听器**：WASAPI 进程环回捕获游戏进程音频 → 高通滤波 + 归一化 + FFT 互相关匹配模板 → 超过阈值触发（防连发 + 自动重启）；
3. **集成**：声音触发作为独立事件流记录日志（可加可选提醒），与画面识别交叉验证。
注意：ok-nte 声音模块为 GPL-3.0 派生（ZZZSoundTrigger），本项目自研实现（WASAPI 为公开 API，互相关为教科书算法），不复制其代码。

## 三、不建议借鉴

- YOLO 训练流水线：AGPL-3.0；本工程仅需 0-9 数字识别，模板匹配已足够。
- SIFT 特征匹配：适用于模板与画面存在缩放差异的场景；本工程固定分辨率捕获，模板匹配更快更稳。
- 异步推理/request 池：本工程识别耗时为毫秒级同步操作，暂不需要；其"延迟销毁防 GIL 死锁"教训记录在案，若未来引入模型推理再采用。

### 借鉴点 1 实测结论（为何不引入 Otsu 自适应二值化）

用 8/7 全部 drop 帧 + 96→9 事件帧实测对比「固定白色掩码 vs Otsu 回退」：

1. **过渡帧像素级真丢失**：96→9 事件帧中，数字 4 在 >150 阈值下都不存在（连半透明笔画都没有），Otsu 无法恢复不存在的像素；该帧信息在捕获时已丢失，**程序拒绝它且不污染基线是正确行为**（下一帧 85 正常接受）。
2. **画面尺度太小**：程序处理的是 190px 宽的整列缩略图（数字仅 ~9px 宽），Otsu 阈值（ret≈120）把 JPEG/缩放伪影全部拉进掩码，导致正常帧（86/34/20 等）识别反而失败——低分辨率下自适应阈值对噪声过于敏感。
3. **结论修正（2026-08-08，黑底纹方案验证后）**：过渡帧存在两种形态——① 数字完全缺失（141102 帧，>150 零像素）；② 半透明残影（154148 帧，亮度 ~150-185）。对形态②，深挖发现**真正的根因是 locate_bar 的条框收缩**：白色组件检测不到残影数字 → 条框右边界收缩 → 残影数字被切在条框外（154148 帧 4 的白色组件其实存在，面积 43，只是被切掉了）。**修复 = 行动值黑底纹定位**（黑底白字中黑底不随数字淡出）：locate_bar 用黑底纹（y 带列亮度剖面 <130 的暗段）扩展条框右边界。实测：54/37/34/27/21 系列丢位帧全部恢复真值，56 项回归通过。黑底区域内的 Otsu 重测：阈值波动大（84/113/134），固定掩码已稳定恢复，**Otsu 无需引入**。

### 借鉴点 2 落地内容

- 新增 `LogGate` 类（ok-nte 精简版）：`allow(key, interval)` 节流 + `allow_message(key, msg, interval, changed)` 消息变化立即放行。
- 未识别日志：同一原因 5 秒内不重复刷屏，原因变化立即记录。
- 数值变化轨迹：回合/行动值每次变化记录一条「数值: 回合X 行动值Y」日志（含启动首条），不变时静默——事后可从 GUI 日志还原完整数值时间线。
- 骤降丢弃日志注明「疑似数字切换过渡帧，像素级缺位，防御正确」，消除"误报"误解。

### 借鉴点 4 落地内容（声音通道）

- `sound_trigger.py`：WASAPI 进程环回捕获（ActivateAudioInterfaceAsync + AUDIOCLIENT_ACTIVATION_PARAMS，Win10 19041+，仅捕获目标进程树音频；comtypes 自研，无 GPL 代码）+ 0.2s 环形缓冲 + 4 阶 butter 高通（1000Hz）+ 归一化 + FFT 互相关匹配；防连发 0.5s、崩溃 1s 自动重启；样本预处理缓存为 .npy（含滤波参数指纹）。
- `sound_sample_collector.py`：从录音按短时能量自动切分候选音效，交互模式逐个播放并命名保存到 `templates/sounds/`。
- 主程序集成：config 新增 `sound_trigger`（默认 False）/`sound_threshold`/`game_process`；GUI 新增「声音触发(需音效样本)」开关；触发写入蓝色「声音: 名称(分数)」事件日志。
- 验证：合成音效单元测试——0.2s 窗口命中分数 0.86、纯噪声 0.03，默认阈值 0.13 区分度充足；切分工具合成录音 2 个候选起止误差在允许范围。
- **待用户实测**：`capture_test.bat` 验证进程环回捕获；采集真实音效样本后启用。

### 借鉴点 3 评估结论（为何不引入识别结果缓存）

- 识别耗时实测 <10ms（16px 高模板 + TM_CCOEFF_NORMED），瓶颈在 PrintWindow 捕获（无法缓存）；
- 游戏画面每帧动画，条区域内容哈希几乎不命中；
- Recorder.record 已有「值变化才存档」的变化检测（同 ok-nte 缓存的目的）；
- 结论：缓存收益 <5%，引入反而增加复杂度，不采纳。
